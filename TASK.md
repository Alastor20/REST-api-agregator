

Индивидуальное задание на курсовое проектирование
Тема: «Разработка многопоточного агрегатора данных из REST API»
- Постановка задачи

На первом этапе, разработать Java-приложение, которое агрегирует данные
минимум из трёх открытых rest api, приводит их к единой модели, сохраняет в
файл (csv или json) и читает из него. На втором этапе приложение опрашивает
источники параллельно и периодически и управляется через собственный rest
api.
- Этап 1: консольное однопоточное приложение
2.1 Выбор API
Необходимо выбрать минимум три открытых API. Каждое из них должно
удовлетворять требованиям:
- JSON-ответ содержит не менее 5 полей, среди которых есть хотя бы один
вложенный объект или массив;
- API принимает query-параметры;
- данные изменяются со временем или в зависимости от параметров.
Списки открытых API можно найти по ссылкам в конце задания, либо взять
свои.
## 2.2 Функциональность
Приложение запускается с параметрами командной строки:
- список API для опроса;
- формат выходного файла (csv или json);
- режим записи (создать новый файл или дозаписать в существующий).
Это обязательный список параметров, по желанию можно добавить свои.
После запуска, выполняется опрос API по списку, ответы записываются в
файл согласно введённым параметрам.
Отдельной командой пользователь может вывести содержимое файла на
экран, целиком или по конкретному API.
2.3 Требования к реализации
При написании кода следует учитывать следующие требования:

- Принципы ООП. Новый API добавляется созданием нового класса без
правки существующей логики (общий интерфейс источника, список или
реестр источников).
- Разделение ответственности: HTTP-клиент, разбор и маппинг в единую
модель, хранилище (интерфейс и реализации для csv и json), агрегация,
## CLI.
- Запрещено  смешивать  логику CLI и  агрегации  данных,  а  также
выполнять HTTP-запросы напрямую из обработчиков ввода.
- Зависимости передаются через конструкторы, сборка объектов вынесена
в один класс.
- Ядро (всё, кроме CLI) не зависит от модуля работы с консолью
- Сборка проекта через Maven или Gradle

3.1 Параллельный опрос
Опрос источников выполняется в многопоточном режиме, по следующим
требованиям:
- Параметры: n — максимальное число одновременно выполняемых задач
(задача = опрос API с конкретными параметрами запроса), t — интервал
опроса в секундах.
- Для каждого API в конфигурации (см. раздел 3.2) задаётся минимум 2
набора  параметров  запроса (например,  разные  города,  валюты  или
категории).
- Одновременно выполняется не более n задач.
- Повторный  опрос  одной  и  той  же  задачи  (тот  же API,  с  теми  же
параметрами)  происходит  не  раньше,  чем  через t секунд  после
завершения предыдущего опроса этой задачи. Если задач больше, чем n,
реальный интервал может оказаться больше t.

- Запись данных в файл потокобезопасна.
- При остановке потоки завершаются, ресурсы освобождаются, данные не
теряются.  Пул потоков  объявлен  бином,  остановка  привязана  к
жизненному циклу контекста.
- Управление потоками вынесено в отдельный компонент-планировщик,
отделённый от бизнес-логики.
- Начало и конец каждого опроса пишутся в лог-файл
o Каждый  опрос  логируется  двумя  строками:  перед  отправкой
запроса [START] и после его завершения [END].
o Завершением считается любой исход: успех, ошибка, таймаут
o Обязательно  указывать: время  с  точностью  до миллисекунд,
событие, название API, параметры  запроса, результат (при
наличии). Пример вывода:
10:00:03.120 [END] weather city=Berlin OK

3.2 Конфигурация приложения
Настройки  приложения  выносятся  в  файл  конфигурации application.yml:
значения  по умолчанию  (n,  t, формат,  путь  к  файлу)  и  наборы  параметров
запросов для каждого API.
3.3 REST-эндпоинты
Имена эндпоинтов можно изменить, если они остаются осмысленными и
описаны в README.
## Эндпоинт Назначение
POST /polling/start Запуск  опроса  (источники с  наборами  параметров,
формат файла, режим записи)
POST /polling/stop Остановка опроса
GET /polling/status Запущен ли опрос, активные источники, параметры n, t
GET /data Содержимое файла с результатами опроса, опционально

В теле /polling/start все  поля  необязательны.  Если  поле  не  передано,
используется значение по умолчанию из application.yml. Если для источника
передан свой список наборов параметров, он полностью заменяет набор из
конфигурации.
Контроллеры тонкие: без бизнес-логики и HTTP-запросов к внешним API.
Неверные параметры дают код ошибки 400, повторный старт уже запущенного
опроса - 409
## 3.4 Тестирование

Тесты  можно  начинать  писать  на  любом  этапе  выполнения  проекта и
покрывают код обоих этапов.
Требования к тестам:
- Покрыты бизнес-логика (разбор ответов, маппинг в единую модель,
хранилища,  агрегация) и  планировщик,  контроллеры  проверены
через MockMvc
- Сетевые вызовы в тестах запрещены, HTTP-клиент мокируется через
## Mockito
- Покрытие по строкам не ниже 70%. JaCoCo подключен к сборке с
проверкой порога, сборка падает, если покрытия не хватает.
- Тесты    многопоточной    логики    стабильны:    используются
CountDownLatch, Awaitility или  подмена  времени,  а  не  просто
одиночный Thread.sleep()
3.5 Критерии принятия этапа
Этап засчитывается, если выполнено всё из этапа 1, соблюдены требования
к n и t,  запись  потокобезопасна,  приложение  корректно  завершается,
эндпоинты отрабатывают  в  позитивных  и  негативных  сценариях,  сборка  с
тестами и порогом покрытия проходит, а студент может объяснить внедрение
зависимостей, жизненный цикл пула потоков и ответить на вопросы по коду.
